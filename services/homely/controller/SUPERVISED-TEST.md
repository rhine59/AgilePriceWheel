# Supervised controller verification — 25 October 2026

The approved bounded live test exercised the production native driver through the
same authenticated HTTPS API used by the app. Automation and heating finished OFF;
the administrative start gate was returned to OFF after cleanup.

## Observed sequence

- Before the test: heating disabled, Automation OFF, saved prices 0p on / 2p off.
- A temporary 35p on/off policy allowed the real 30.06p effective-price slot.
- The controller correctly waited for 18:00 rather than starting mid-slot.
- At 18:00:17 UTC it reported a confirmed native boost for the 18:00–18:30 slot.
  This phase requires the start response and compact getter readback to match.
- At 18:00:26 UTC the original complete policy was restored at a new revision.
- The controller completed its policy-driven stop. The subsequent app OFF
  command response already reported `heating_off` at 18:00:54 UTC. Later status
  showed the old automatic control gate true, price permission false and heating
  disabled, before the OFF worker acknowledged `automation_off`.
- The OFF state survived container recreation. Independent settings readback
  confirmed heating disabled. Heating schedules and hot-water settings/schedules
  matched their baselines; temporary override timestamps may be regenerated by
  Homely mode changes. No temperature or schedule setter was sent.

This was a controlled policy-threshold change using real prices, not a naturally
occurring tariff-boundary price crossing. The earlier separate half-hour pilot
verified native expiry; this test was cancelled before its accepted expiry.
Reported state/command acknowledgements are not a physical electricity meter.

## Harness timeout and reviewed result

The original harness reported failure because its 15-poll wait ended before the
policy-stop acknowledgement, which arrived about 28.3 seconds after restoring the
policy. The original private record remains unchanged. Reviewed response ordering
confirms that the policy stop completed before the app OFF request was accepted:
its response already contained `phase=heating_off`, and the control worker's
subsequent status still represented an automatic-policy tick, not the OFF path.
No emergency direct-stop fallback was used. The live functional start/stop checks
are therefore verified on review; the original harness itself did not pass.

## Follow-up improvements

The run exposed two usability/concurrency issues, now fixed and deployed:

1. Explicit OFF is persisted immediately without waiting behind a slow Homely
   control tick. A dedicated store lock serializes switch revisions. Starts
   recheck saved OFF before enabling, before starting a boost and after an
   in-flight start returns; pending shutdown never means confirmed physical off.
2. Old policy revisions, expired slot decisions and unavailable source data no
   longer appear as current price permission while the worker finishes a stop.

Six new regression checks cover these cases. All 135 backend checks pass. The
actuation payloads are unchanged; no further live heating boost was run for these
follow-up changes. The app's ten focused checks remain applicable, and the full
Python service walkthrough is available for offline verification.

## Readiness and limits

The live command cycle is verified for this installation. Administrative
activation for ongoing app use is a separate approval from the bounded test.
Automation remains OFF, its saved prices are restored, and ON remains blocked
until that separate activation is approved.

The API is observed rather than a published supported contract. NAS/controller or
cloud outages can delay shutdown: native boost expiry alone leaves normal heating
enabled. Homely can take tens of seconds to confirm a change. Respect pending/error
states; the software does not promise instantaneous shutdown, atomic ownership
against simultaneous app edits, or formal vendor certification. An unattended
long-running cycle has not been tested in this session.
